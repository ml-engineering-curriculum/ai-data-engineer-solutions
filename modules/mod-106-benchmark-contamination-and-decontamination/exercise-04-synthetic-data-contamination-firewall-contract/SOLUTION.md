# Exercise 04 — The Synthetic-Data Contamination Firewall Contract (Solution)

## 1. Solution overview

This is a **design** exercise. The learner writes the operating
contract between the team that produces synthetic pretraining data
(`mod-108`) and the team that ingests it into the pretraining
mixture — a contract whose entire purpose is to ensure no eval
suite contaminates the training mixture through the synthetic
channel. The deliverable is a four-page `CONTRACT.md` plus a
machine-readable `firewall_manifest.schema.json` that both teams
sign.

The exercise is design-only. No model runs, no pipeline is stood
up end-to-end; the learner demonstrates they can specify a
firewall contract that the rest of `mod-106` and `mod-108` would
implement against. The output is reviewable by peers in exactly
the same way a service-level agreement is reviewable: it is a
contract, with promises, counterparty obligations, and a
measurement surface.

Deliverables:

- `CONTRACT.md` — the operating contract. Four pages, two
  signatories, one versioning rule.
- `firewall_manifest.schema.json` — the JSON Schema the synthetic
  generator must emit alongside every batch of synthetic data.
- `rationale.md` — the decision log: which clauses are negotiable,
  which are load-bearing, and why.
- `worked_example/manifest.json` — one complete manifest instance
  that satisfies the schema, used in review to show the contract
  is operable.
- A section inside Exercise 01's `contamination_report.yaml` —
  `§9 synthetic_channel` — that references the contract version
  and the per-batch manifest SHA-256s.

Governance framing. Synthetic data generated by an LLM that saw
eval benchmarks during its own training is a **supply-chain
contamination channel** for the model that ingests the synthetic
output. The OWASP ML Top 10 anchors are **ML02:2023 Data Poisoning
Attack** (the harm) and **ML06:2023 ML Supply Chain Vulnerabilities**
(the mechanism). MITRE ATLAS **AML.T0019 Publish Poisoned Datasets**
is the adversary-facing technique. NIST AI RMF **GOVERN 6.1**
(policies and procedures are in place to address AI risks and
benefits arising from third-party software and data) is the
governance anchor that justifies a contract instead of an
informal understanding.

## 2. Implementation — worked answer (the contract)

### 2.1 `CONTRACT.md` — structure

```markdown
# Synthetic-Data Contamination Firewall Contract — v1

| Field                | Value                                                      |
|----------------------|------------------------------------------------------------|
| Contract version     | 1.0.0                                                      |
| Effective            | 2026-11-17                                                 |
| Producers (sign)     | synthetic-data team lead, synthetic-data generator owner   |
| Consumers (sign)     | ai-data-engineer (slice owner), ai-risk-engineer (peer)    |
| Supersedes           | n/a                                                        |
| Review cadence       | every 90 days or on generator upgrade                      |

## 1. Scope

This contract governs every batch of synthetic pretraining data
that the producer ships to the consumer under the batch-id namespace
`synth-<producer>-<yyyyWw>-*`. It does NOT govern synthetic
*fine-tuning* data (RLHF labels, instruction-following pairs); a
separate contract covers that channel.

## 2. Promises the producer makes

### 2.1 Decontaminate against the consumer's firewall

Every batch is scanned against the consumer's
`eval_index.parquet` (Exercise 01) **before** shipping. The
producer uses the same `N = 13`, the same canonical form, and
the same xxh3-128 fingerprint as the consumer's firewall. Any
document with ≥ 1 matching eval n-gram is dropped before the
batch is sealed.

### 2.2 Prohibit the eval set from entering the generator's prompt

The generator must never see the consumer's eval shards in its
input context. The producer attests, per batch, that:
- The generator's retrieval index is **disjoint** from
  `eval_index.parquet`. (Disjointness is demonstrated by scanning
  the retrieval index against the eval index and reporting zero
  overlap in the batch manifest.)
- The generator's system prompt and few-shot examples do not
  include eval records verbatim or in paraphrase.

### 2.3 Record the generator provenance

Every batch manifest lists the generator model id, the model's
training-cutoff date, the model's own published decontamination
report (link + SHA-256), and the retrieval index's content hash.
A producer whose generator has no published decontamination
report may not ship under this contract.

### 2.4 Attest the generation chain is single-generator

If the batch is produced by a pipeline of generators, every
intermediate generator's decontamination report must be in the
manifest. A two-stage pipeline where the second generator is
clean but the first is not fails the firewall.

### 2.5 Hand off a signed manifest

The batch manifest — schema in `firewall_manifest.schema.json` —
is signed with the producer's cosign key. The consumer's acceptance
pipeline fails the batch if the signature does not verify.

## 3. Promises the consumer makes

### 3.1 Publish the eval index

The consumer ships `eval_index.parquet` plus `eval_index.parquet.sha256`
to the producer no fewer than seven calendar days before a
scheduled batch. The eval index is a frozen artifact at the
contract-version level; a new eval suite added to the firewall
is a contract-version bump.

### 3.2 Publish the canonical form and `N`

Both are pinned in Exercise 01's `policy_note.md`. The consumer
ships a copy with the eval index.

### 3.3 Run the consumer-side firewall anyway

The consumer runs Exercise 01's firewall over every accepted
batch. The producer's attestations are necessary but not
sufficient; the consumer's independent scan is the second signal.
This is defense-in-depth, not duplication.

### 3.4 Respond to a `pending_review` batch within five business days

A batch that lands in `quarantine_review` sits in the peer's queue
for at most five business days before the producer is notified
of a verdict.

## 4. The measurement surface

Every batch produces a row in `metrics/batches.parquet`:

| Column                          | Type       | Notes                                                 |
|---------------------------------|------------|-------------------------------------------------------|
| batch_id                        | string     | `synth-<producer>-<yyyyWw>-<counter>`                 |
| producer                        | string     |                                                       |
| contract_version                | string     | Must equal the active contract-version (semver).      |
| eval_index_sha256               | string     | What the producer scanned against.                    |
| generator_model_id              | string     |                                                       |
| generator_cutoff_date           | date       |                                                       |
| retrieval_index_sha256          | string     |                                                       |
| producer_scanned_doc_count      | int        |                                                       |
| producer_dropped_doc_count      | int        | Should be ≤ 0.1% of scanned docs on a clean channel.  |
| manifest_sha256                 | string     |                                                       |
| manifest_signature_verified     | bool       |                                                       |
| consumer_firewall_verdict       | enum       | `clean` / `quarantine_review` / `rejected`            |
| consumer_matched_docs           | int        | Consumer-side independent scan. Expected 0.           |

A `consumer_matched_docs > 0` on a batch whose
`producer_dropped_doc_count > 0` is **not** a contract breach — the
producer attested to a scan, not to zero false negatives. A
`consumer_matched_docs > 0` on a batch whose
`producer_dropped_doc_count == 0` **is** a contract breach, because
the producer attested to scanning yet shipped a matching document.

## 5. Breach handling

| Breach class                           | Trigger                                                                           | Response                                                 |
|----------------------------------------|-----------------------------------------------------------------------------------|----------------------------------------------------------|
| Signature failure                      | `manifest_signature_verified == false`                                            | Batch rejected; producer paged within 1 business day.    |
| Attestation mismatch                   | Producer attests zero drops yet consumer firewall matches ≥ 1 doc                 | Batch rejected; producer root-causes within 5 bus. days. |
| Generator cutoff newer than eval shard | Generator's cutoff ≥ the eval shard's publication date — generator is suspect     | Consumer requests an external decontamination audit.     |
| Retrieval-index overlap                | Producer's own attestation of disjointness returns overlap > 0                    | Batch held; producer rotates the retrieval index.        |

## 6. Versioning

Contract follows SemVer at the document level. **Major** bumps on
any of: tokenisation change, `N` change, canonical-form change,
addition of a new eval suite to the firewall, change to the
signing root of trust. **Minor** bumps on measurement-surface
additions. **Patch** bumps on wording clarifications.
```

The worked example uses placeholder hashes for review — in
production the hashes are the real artifacts' SHA-256s. The
`dropped_doc_count: 42` on 1.2M scanned docs (= 3.5e-5) is in the
range §4 flags as normal-channel; a batch reporting
`dropped_doc_count: 0` on a non-trivial batch would itself look
suspicious and warrant a consumer-side spot audit.

### 2.4 `rationale.md` — the decision log

The rationale covers each contract clause and answers:

- **Why is this clause in the contract at all?**
- **What does the clause prevent?**
- **What does it not prevent?**
- **What would break if the clause were weaker?**

Representative entries:

- **§2.1 "Decontaminate against the consumer's firewall" is
  load-bearing.** It means the two teams share one normative
  definition of contamination (`N = 13`, canonical form), so a
  "the producer defines decontamination differently" dispute
  cannot arise.
- **§2.2 "Prohibit the eval set from entering the generator's
  prompt" is a separate clause from §2.1.** A generator can be
  perfectly decontaminated at output time and still memorise
  prompts; decontaminating the output is not the same as
  decontaminating the inputs.
- **§3.3 "Run the consumer-side firewall anyway" is deliberate
  duplication.** Producer attestations are a cooperative control;
  consumer scans are a verification control. Removing either
  reduces the control surface by half.
- **§6 "Major bump on new eval suite" is intentionally heavy.**
  A contract-version bump forces the producer to re-run their
  scan under the new eval set; without this clause, a new eval
  could be added by the consumer and silently not scanned.

### 2.5 Extending Exercise 01's `contamination_report.yaml`

The report gains a `§9 synthetic_channel` block:

```yaml
synthetic_channel:
  contract_version: 1.0.0
  contract_sha256: <sha256 of CONTRACT.md at the batch's time>
  batches:
    - batch_id: synth-example-2026W46-01
      manifest_sha256: <...>
      consumer_firewall_verdict: clean
      consumer_matched_docs: 0
```

The report publishes one row per ingested batch. `mod-109` signs
the extended report as a unit.

## 3. Validation steps

1. **Schema validates the worked example.**
   `jsonschema -i worked_example/manifest.json
      firewall_manifest.schema.json` exits 0.
2. **Contract is signed by both sides.** `CONTRACT.md` ends with
   two cosign signature paths; both signatures verify.
3. **Version is pinned.** `grep "Contract version" CONTRACT.md` is
   identical to `jq -r '.contract_version'
      worked_example/manifest.json`.
4. **Measurement surface rows are complete.** Every column in §4
   of `CONTRACT.md` has a corresponding JSON Schema field; a
   missing column fails this check.
5. **Breach-handling table has at least one trigger per OWASP ML Top
   10 ML02 and ML06 failure mode.** Signature failure covers
   ML06; attestation mismatch covers ML02.
6. **Retrieval-disjointness clause is in the manifest.** A
   manifest claiming "decontaminated output" without an
   independently-provable disjoint retrieval index fails the
   contract.
7. **No invented facts.** The contract cites generator model ids
   as placeholders, not as endorsements. Any specific vendor name
   is documented in `rationale.md` with a citation before
   publication.

## 5. Common mistakes

- **Letting the producer define decontamination.** Each team's
  "clean" is different; the contract must bind both teams to one
  definition (the consumer's firewall, per §2.1).
- **Scanning only the generator output.** A generator that saw
  eval records in its prompt will leak them even if the output
  passes an n-gram scan. §2.2 is a separate clause for a reason.
- **Removing the consumer-side scan.** "The producer attested" is
  not a verification control; it is a cooperative control. Keep
  both.
- **Treating `dropped_doc_count: 0` as "cleanest".** A zero on a
  non-trivial batch is a red flag — either the producer did not
  scan, or their scan is miscalibrated. The rationale log must
  say so.
- **Omitting retrieval-index disjointness.** A generator that
  retrieves from a corpus containing the eval set bypasses every
  output scan.
- **Versioning the contract with a rolling tag.** SemVer at the
  document level is a hard requirement — a rolling tag means every
  past batch is implicitly under the latest contract version,
  which breaks reproducibility.
- **Signing the contract without a review cadence.** A 90-day
  review cadence prevents contract drift as new eval suites or
  new generator models land.
- **Treating "synthetic" as one channel.** This contract covers
  pretraining synthetic data. RLHF and instruction-tuning synthetic
  data need their own contract.
